QA Dashboard

Unified test coverage visualization across the entire project

Why I built it

Test results were scattered across different places - Playwright reports, .NET .trx files, separate CI runs - with no single view of how much of the actual product was covered by tests and where the gaps were.

What problem it solves

  • Merges results from two different test stacks (Playwright/JS frontend + NUnit/.NET backend) into one unified dashboard.
  • Shows not just "how many tests pass," but which critical product features actually have coverage - via a risk-weighted score (critical modules count more than low-risk ones).
  • Surfaces coverage "blind spots" - modules with zero passing tests.
  • Tracks trends over time (coverage history across runs), instead of each CI run being an isolated snapshot.
  • Auto-generates and publishes to a live URL after every CI run, so the whole team (QA, devs, PM) can see the current state without going into GitHub Actions.

AI Test Generator

Auto-generates QA test plans and test cases from Jira tickets

Why I built it

Writing detailed test plans (functional, negative, edge case, regression) for every new feature manually is slow and repetitive, and it's easy to miss cases when working straight from a ticket description instead of the actual implementation.

What problem it solves

  • Takes a Jira ticket ID and automatically produces a complete test plan + test cases, instead of a QA writing them by hand from scratch.
  • Bases the generated tests on the actual code (both backend and frontend repos), not just the ticket text - so it catches edge cases, validations, and error handling that aren't mentioned in the ticket description.
  • Delivers the result directly into a shared Google Sheet (from a template), ready for the QA to review and execute - no manual formatting or copy-pasting.
  • Notifies by email when generation is done, so there's no need to babysit the process (which takes a few minutes per ticket).
  • Can be triggered automatically via a Jira webhook when a ticket changes, removing the manual step entirely.

How it works

  1. You run ./generate.sh IN-184 (or it triggers automatically via a Jira webhook when the ticket changes).
  2. A Python script fetches the ticket (summary, description, acceptance criteria) from Jira through the Jira REST API.
  3. It builds a detailed QA prompt and feeds it to the Claude Code CLI, pointing it directly at the real backend (Laravel) and frontend (Vue.js) repos so it analyzes the actual implementation, not just the ticket text.
  4. Claude returns structured test cases (functional, negative, edge case, regression), which the script parses into JSON.
  5. The parsed result is written into a new Google Sheet, copied from a shared template, via the Google Sheets/Drive API.
  6. An email notification is sent once the sheet is ready, with a link to it.
  7. Optionally, a small Flask webhook server (exposed via Cloudflare Tunnel) listens for Jira ticket updates and re-triggers the whole flow automatically, ignoring irrelevant changes like status or assignee updates.

QA Test Copilot

A custom /qa-test Claude Code command that code-reviews, live-tests, and documents a ticket end-to-end

Why I built it

Testing a ticket end-to-end always meant repeating the same tedious sequence by hand: reading the code, checking the database, hitting the API, testing the UI, then re-testing on the mobile app - and writing up the findings in a way a developer could actually act on took just as long as the testing itself.

What problem it solves

  • Turns a single command, /qa-test 19, into a full QA pass on a specific ticket: pulls the latest code, looks up the ticket number and its description, and locates exactly where and how it was implemented in the Laravel codebase.
  • Runs a detailed code review of the change first - including how it touches other modules - to catch logic and integration issues before any test is even executed.
  • Runs real functional tests two ways on the backend: direct API requests plus Laravel Tinker and database checks, and separately drives the UI live through Playwright MCP.
  • Extends the same testing pass to the mobile app by launching an Android Studio emulator and running live test flows, taking screenshots along the way to track progress and decide what to check next.
  • Writes every issue it finds into a developer-ready Markdown report: what's broken, exact steps to reproduce, the actual effect, and why it's happening - everything needed to fix it without back-and-forth.
  • Persists everything into a session Markdown file, so a QA pass can be resumed exactly where it left off instead of losing context between sessions.

How it works

  1. You type /qa-test 19 in Claude Code, where 19 is the ticket number.
  2. Claude pulls the latest changes from the repo and looks up ticket #19's description in the tracker.
  3. It searches the PHP/Laravel codebase to find exactly where and how the ticket was implemented.
  4. It code-reviews that implementation, tracing how it interacts with other modules to flag risky or broken integrations before testing starts.
  5. It runs backend tests via direct API calls, Laravel Tinker, and database queries, then runs live UI tests through Playwright MCP.
  6. It launches the mobile app in an Android Studio emulator and runs live test flows, capturing screenshots to track state and guide the next test step.
  7. Every issue found is written into a Markdown report formatted for handoff: the bug, reproduction steps, the effect, and the root cause.
  8. Everything is saved into a session Markdown file, so the QA process for that ticket can be picked up later without losing history.
